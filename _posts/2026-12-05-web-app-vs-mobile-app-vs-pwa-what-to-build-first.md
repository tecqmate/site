"We need an app" is one of the most common sentences a development team hears, and one of the least clear. Do you need a mobile app from an app store? A web app that works in the browser? Or something in between?

The answer changes the cost, the timeline and the way customers find you. This guide explains the main options and helps you decide what to build first.

## Quick answer

For most new products, **start with a web app** (or a responsive website) that works well on phones and computers. Build a **native mobile app** when you need deep phone features, frequent daily use or app store presence. A **progressive web app (PWA)** can be a useful middle step. The best first version is the smallest one that lets real users do the main task.

## The options in plain language

### Website

A set of pages people read. It is mostly for information, such as company details, services, blog posts and contact forms.

### Web app

A product you use in the browser, with logins, data and actions. Examples are a booking system, a customer portal, a dashboard or an online store. It works on any device with a browser, with nothing to install.

### Native mobile app

An app built for a specific phone system (such as iOS or Android) and installed from an app store. It can use phone features such as the camera, notifications, location and offline storage in depth.

### Cross-platform mobile app

One codebase used to build apps for both iOS and Android. It can reduce cost compared with building two separate native apps, though some advanced features may still need platform-specific work.

### Progressive web app (PWA)

A web app that can be added to the home screen and can work in a limited way offline. It feels more like an app but is delivered through the browser. Support for some features differs between phone systems and changes over time, so check what your needs require.

## Side-by-side comparison

| Factor | Responsive website | Web app | PWA | Native or cross-platform app |
| --- | --- | --- | --- | --- |
| Where users find it | Search and links | Search and links | Search, links, home screen | App stores, plus links |
| Installation | None | None | Optional | Required |
| Phone features | Limited | Limited | Some | Full |
| Works offline | No | Rarely | Partly | Yes, if designed for it |
| Updates | Instant | Instant | Instant | Release and store review |
| Relative build effort | Lowest | Medium | Medium | Highest |
| Best for | Information and leads | Business tools, portals | Light app-like use | Daily-use consumer apps |

## Which one fits your situation?

| Your situation | Often suitable |
| --- | --- |
| You want to explain your services and get enquiries | Responsive website |
| Staff or customers need to log in, book, order or track | Web app |
| You want an app-like experience but a small budget | PWA |
| Your product needs camera, background location, Bluetooth or push alerts every day | Native or cross-platform app |
| You want to test an idea quickly | Web app or simple prototype first |
| Your customers expect to find you in the app store | Native or cross-platform app |
| Your users are mostly office workers on computers | Web app |

## Questions to ask before you decide

1. **What is the one main task users must complete?** Build for that first.
2. **How often will people use it?** Daily-use products fit apps. Occasional use fits the web.
3. **Do you need phone hardware?** If you need deep camera, sensor, Bluetooth or background features, native is likely required.
4. **How will people discover you?** Search and links favour the web. App store search favours apps.
5. **Who are your users and what devices do they have?** Check your analytics or ask a sample of customers.
6. **What is your budget and deadline?** Two native apps plus a backend cost more than one web app.
7. **Do you need to work offline?** If yes, plan for it from the start.
8. **What will you do after launch?** Apps need updates for new phone versions and store rules.

## Costs and trade-offs to be aware of

- **Backend and admin work is shared.** Whatever you choose, you will probably need a server, a database, user accounts and an admin panel. This is often a large part of the project.
- **Native apps have extra costs.** These include developer accounts, store review processes, testing on many devices and updates for new phone system versions.
- **App stores have rules and fees.** Rules on payments, privacy and content apply, and they change. Check the current terms.

- **Design effort differs.** Mobile screens need careful design for small displays and touch.

## A sensible path for most businesses

1. **Define the core task and the users** in a short project brief. See our guide on [writing a software project brief]({{ '/2026/11/23/how-to-write-software-project-brief-rfp-template/' | relative_url }}).
2. **Build a minimum viable version as a web app.** Make it work well on phones.
3. **Watch how people use it.** See which tasks they repeat and what they ask for.
4. **Add app-like features** with a PWA if that is enough.
5. **Build a native or cross-platform app** when you have clear evidence that it is worth the cost, for example when users ask for features only an app can give.

This path lowers risk because you learn from real users before making the biggest investment.

## Decision checklist

- ✅ You can describe the main task users want to complete in one sentence
- ✅ You know how often people will use the product
- ✅ You have checked which phone or computer features you really need
- ✅ You know how customers will find the product
- ✅ You have compared the cost of a web app with an app for iOS and Android
- ✅ You have planned the backend, admin panel and user accounts
- ✅ You know who will maintain and update the product after launch
- ✅ You have decided what the first version will leave out
- ✅ You have a clear measure for success after launch

## Common mistakes

- **Building two native apps first** before knowing whether anyone wants the product.
- **Choosing an app because competitors have one.** Ask what your users actually need.
- **Forgetting the backend.** The visible screens are only part of the work.
- **Ignoring the web experience.** Many users start on the web even if you also have an app.
- **No plan for updates.** Apps need regular work to keep running on new phone versions.
- **Trying to build everything in version one.**

## FAQ

**Is a PWA as good as a native app?**
Not for every case. A PWA works well for many light, app-like uses. Native apps are stronger for deep device features and for being found in app stores. Check current browser support for the features you need.

**Is cross-platform cheaper than native?**
Often, because one team builds one codebase for both phone systems. But complex features may still need platform-specific work, so ask for an estimate for your product.

**Can I start with a web app and add a mobile app later?**
Yes, and it is common. A good backend can serve both. Ask your team to design it that way from the start.

**Do I need an app to take payments or bookings?**
Not necessarily. Many businesses do this well on the web. Check the payment and platform rules for the route you choose.
